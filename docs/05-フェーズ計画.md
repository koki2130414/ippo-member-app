# 05. フェーズ計画

各フェーズの終わりに `npm run verify`（lint → typecheck → test → build）を通してから報告する。
Phase 2 以降は E2E（`npm run e2e`）も完了条件に入る。

## Phase 1 — 基盤 ✅（この報告）

作るもの
- プロジェクト雛形（Next.js 16 / TypeScript strict + `noUncheckedIndexedAccess` / Tailwind v4 トークン / ESLint / Vitest / Playwright 設定）
- ESLint で仕様の禁止事項を機械的に止める: `any`、`as` による型アサーション（`as const` は可）、非 null アサーション、`alert/confirm/prompt`、`console.log`、domain からの React/Next/Supabase import、components からの data 層 import
- ドメイン層一式（types / dto / plans / points / authorization / scoring / schedule / members / jst / schemas）
- DataStore インターフェースと mock 実装、seed（empty / sample）
- サービス層の土台: Actor の組み立て、認可ガード、監査ログ、ポイント（付与・加点・残高・交換）、会員（追加・プラン割り当て・削除）

完了条件
- [x] `npm run verify` が通る
- [x] Vitest: プラン判定、ポイント（冪等・日次上限・JST 境界・同時アクセス）、認可（4ロール × 主要リソース）、診断採点、クラス開催日、会員削除、DTO から秘密フィールドが落ちていること
- [x] 環境変数ゼロで `npm run build` が通る

- `/login`（デモモードだけロール別ワンクリックログイン `demo-login-student` など）、`/register`、`/reset-password`、`/onboarding`、`/forbidden`

- `/home`（生徒ダッシュボード: 連続記録・ポイント・次のクラス）、`/guardian`、`/coach`、`/admin` の入口

  - 4ロールそれぞれ、入れない画面がサーバー側でも 403 / `/forbidden`

## この順番にした理由

- RLS を最後に置いているのは、**先にサービス層の認可（本丸）とテストを固め、その表を SQL に写す**ほうがずれが少ないため。RLS が無い間は本番公開しない（Phase 6 完了が公開の前提）。
- 画面より先にドメインとサービスを作ったのは、世界観のルール（言い分け・比較しない・途切れても責めない）を1か所に閉じ込め、画面ごとにぶれないようにするため。
