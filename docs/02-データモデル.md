# 02. データモデル

型の定義は `src/domain/types.ts`。ここでは「なぜこの形か」と、テーブルにしたときの制約を書く。

## 原則

1. **日時は UTC で保存し、JST の暦で数える。** 「今日」「今月」「日次上限」の判定は `src/domain/jst.ts` だけが行う。Vercel（UTC）と開発機（JST）で結果が変わらないよう、ローカルタイムゾーンのメソッドは使わない。Vitest は `TZ=America/Los_Angeles` で走らせて、JST 変換の抜けを炙り出す。
2. **クライアントに渡す型は別名にする。** 秘密フィールドは `Omit` で型から落とし、さらに変換関数で「渡してよいキーだけを書いて組み立てる（許可リスト）」。スプレッドで丸ごと渡さない。
3. **個人情報は公開用と非公開用で分ける。** `PublicProfile` に本名・メールを持たせない（型に無いので、表示しようがない）。
4. **消さずに印をつける。** チャットの削除・非表示、退会は行を残して印（`deletedAt` / `hiddenAt`）をつける。監査で経緯を追えるようにするため。ただし退会者の個人情報そのものは消す。

## ポイント（テーブル設計）

```sql
create table point_transactions (
  id uuid primary key,
  user_id uuid not null references profiles_private(user_id),
  amount integer not null check (amount <> 0),
  reason text not null,
  idempotency_key text not null unique,   -- 二重付与を DB で止める
  jst_date date not null,                 -- 日次上限の判定用（JST の暦日）
  created_at timestamptz not null default now(),
  created_by uuid not null,
  note text
);
create index on point_transactions (user_id, reason, jst_date);
```

- 残高カラムは作らない。残高は `sum(amount)`。重くなったら「取引履歴から作るマテリアライズドビュー」にする（正は常に履歴）。
- 付与は `append_point_transaction(tx, max_per_day)` という RPC（Postgres 関数）で、**冪等キーの確認・日次件数の確認・挿入を1トランザクション**で行う。同じ利用者・同じルールの行を `pg_advisory_xact_lock` で直列化し、同時アクセスで上限を超えないようにする（Phase 6）。mock では同じことを await を挟まずに行っている。
- 交換も `exchange_points(item_id, debit)` RPC で、残高確認・在庫の条件付き減算（`update … set stock = stock - 1 where stock > 0`）・引き落としを1トランザクションで行う。

## seed

| 種類 | 中身 | いつ |
|---|---|---|
| `empty`（既定） | 運営1人、プラン5、ポイントルール、クラス4枠、講義カテゴリー、診断の定義と設問 | 何も指定しないとき |
| `sample` | 上に加えて、架空のコーチ2・生徒3・保護者1、紐付け、動画3本（配信元3種）、ノート、レビュー、ポイント、交換品 | `IPPO_SEED=sample` |

sample の人物は、表示名に「（サンプル）」、本名に「架空」を入れ、メールは届かない `@example.invalid`。ID は `u-student-0001` のように名前を含めない固定値。
