# 03. 認可とセキュリティ

## 3層で強制する

```
リクエスト
  │
  ▼
① src/proxy.ts            ルート単位の粗い判定（未ログイン→/login、ロール違い→/forbidden）
  │                        domain/authorization.ts の rolesAllowedForPath を使う
  ▼
② サービス層のガード       requireActor / requireRole / requireAdmin / requireStudentAccess
  │  （ここが本丸）         判定の中身は domain/authorization.ts。拒否なら ServiceError("forbidden")
  ▼
③ Supabase RLS            同じ認可マトリクスを SQL で書き直したもの（最後の砦）
```

- **画面での出し分けは認可ではない。** ボタンを隠しても、②と③で同じ判定を必ず行う。
- 判定の定義は `src/domain/authorization.ts` の1か所だけ。②はそれを呼び、③は下の表を SQL にしたもの。表を変えたら `authorization.test.ts` と RLS のポリシーテストの両方を直す。
- `Actor`（いまの利用者）は**セッションの userId から DB を読んで組み立てる**（`server/services/actor.ts`）。ロールや担当範囲をクッキーやフォームの値から作らない。退会者は未ログイン扱い。
- 迷ったら拒否。許可は後から足せるが、漏れた情報は取り戻せない。

## 認可マトリクス

| 操作 | 生徒 | 保護者 | コーチ | 運営 |
|---|---|---|---|---|
| 生徒の情報を見る（進捗・ポイント・ノート・レビュー・診断結果） | 自分 | 紐づいた子 | 担当生徒 | 全員 |
| ノート・プレー動画・ふりかえりを出す | 自分 | × | × | × |
| ノート・レビューに返信、個別メニュー作成 | × | × | 担当生徒 | ×（閲覧のみ） |
| 出欠の記録 | × | × | 担当クラス | ○ |
| ポイント: system ルール（ログイン等） | 行動の成立をサーバーが確認して付与 | × | × | × |
| ポイント: コーチ加点など | × | × | 担当生徒 | ○ |
| ポイント: 運営調整・イベント | × | × | × | ○ |
| 1対1チャンネルを見る | 自分の | 紐づいた子の | 自分が入っている | ○（監査） |
| 1対1チャンネルに書く | 自分の | 紐づいた子の | 自分が入っている | ×（非表示などのモデレーションのみ） |
| クラス全体チャンネル | 参加クラスを読むだけ | × | 書ける | ○（監査） |
| 管理画面 | × | × | × | ○（すべて監査ログへ） |

各マスは `authorization.test.ts` にテストがある。

## 動画

| 配信元 | クライアントに渡すもの | 再生のしかた |
|---|---|---|
| アプリ内アップロード（既定） | `VideoSummary`（ストレージのパスなし） | 再生ボタンで **POST** → サーバーが会員権限を確認 → 短い期限（例 5 分）の署名URLをレスポンスで返す |
| Mux Signed Playback | `VideoSummary`（playbackId なし） | 再生ボタンで **POST** → サーバーが会員権限を確認 → playbackId と期限付き JWT をレスポンスで返す |
| YouTube（`youtube-nocookie.com`） | `youtubeId` を含む | 埋め込み。**アプリの外でも見られる**ことを、管理画面の入力欄と生徒側の再生画面の両方に赤字で出す |

- 署名トークン・playbackId・storageKey は **HTML・RSC ペイロード・GET レスポンスに載せない**。POST のレスポンスでだけ返す。
  E2E で「ページの HTML に `"storageKey":` や `"muxPlaybackId":` が現れない」ことを assert する（Phase 3）。
- YouTube の ID だけは渡す。ID が分かれば誰でも外で見られるので、隠しても守ったことにならない。守れない約束を UI で装わない。
- 右クリック禁止は**セキュリティ対策として扱わない**。入れるとしても「気休め」とコメントに書く。画面録画・ダウンロードは技術的に防げないことを運営に伝える（README）。

## クイズ・診断

- 回答送信前にクライアントへ渡すのは `QuizQuestionPublic` / `DiagnosisQuestionPublic` だけ（`isCorrect` と解説を型ごと落とす）。
- 採点は Server Action → サービス → `domain/scoring.ts`。設問に無い選択肢IDは不正解。設問0件は合格にしない（ポイントの抜け道にしない）。

## 鍵と秘密値

- `SUPABASE_SERVICE_ROLE_KEY`、`MUX_SIGNING_PRIVATE_KEY`、`IPPO_SESSION_SECRET` はサーバー専用。`NEXT_PUBLIC_` を付けない。
- 秘密値を読むモジュール（`server/env.ts`、`data/index.ts`）は `import "server-only"` でクライアントから import できないようにしている。
- `.env.example` には名前だけ。値はコードに書かない。

## 未成年者保護

- 生徒同士の DM は作らない（`ChatRoomKind` に存在しない）。
- コーチ⇔生徒の連絡は、運営が閲覧できる監査対象チャンネル。保護者も同じルームを見られる。
- メッセージの編集・削除・非表示は監査ログ（`chat.message_edit` / `chat.message_delete` / `chat.message_hide`）に記録する。行は消さない。
- 公開プロフィールに本名を出さない（`PublicProfile` 型に `fullName` が無い。`dto.test.ts` で型レベルでも確認）。
- アバターはプリセットから選ぶだけ。顔写真は受け付けない。
- 生年月日は保存しない。年代だけ。

## ログと監査

- `console` を直接使わず `server/logger.ts` を通す（ESLint で `console.log` を禁止）。キー名から機密と分かる値は伏せる。
- 監査ログの `metadata` には識別子と変更内容（例: `{ from: "light", to: "soccer_iq" }`）だけ。本文・本名・メール・自由記述は書き写さない（テストで確認）。
- 運営の操作もすべて監査対象。

## ヘッダー

`next.config.ts` で `X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options: DENY`、`Permissions-Policy` を全ページに付けている。CSP は動画プレイヤーの配信元が確定する Phase 3 で締める。
